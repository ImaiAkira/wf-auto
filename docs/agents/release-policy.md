# 什么时候该发 Release

> 起因：2026-10-18 一晚发了 4 个 Release（v1.0.0 → v1.0.3），其中两个 0 下载，
> 改的只是界面文案和一个注释里的代号。
> 运维原话：**「不要这么急着就发版，这些都是小 fix，提交就是了」**、
> **「我们不能随便发版，最好把一些改动都攒在一起一起发」**。

## 一句话

**默认不发。改动先攒在 `main` 上，攒够一批再发一次。**

`main` 随时可以领先 tag；用户拿到的永远是**上一个** Release。这是正常的，不是欠账。

## 攒什么

以下全部**只提交到 `main`**，不动 `assets/interface.json` 的 `version`、不打 tag、不发 Release：

- 注释 / 测试 / 内部重构 / 文档
- 界面文案微调
- 脱敏类（代号、路径、账号标识）—— 只要它还没在**线上包里**暴露
- 单个功能点的半成品（用户还看不出一条完整路径时）

## 什么时候真的发

攒够了、且满足**至少一条**：

1. **有一条用户能完整用上的新能力**（新任务、某场景从「不能打」变成「能打」）
2. **有一批用户能感知的修复**（不是一条，是几条凑一起值得让人升级）
3. **线上包坏了**（缺文件 / 起不来）→ 立刻发，这是修坏包
4. **线上包里真的漏了隐私**（不是「将来可能」，是现在下载得到）→ 立刻发

第 3、4 条是仅有的两个「不用攒」的例外。

## 怎么判断「用户能感知」

问自己一句：**用户照 README 用一遍，会不会看出不一样？**

- 会 → 进攒批清单，等下一次发
- 不会（只有看代码/日志才知道）→ 只提交，连清单都不用进

## 为什么

- Releases 是给用户的「版本」概念。一晚四个版本会让人以为出了大事故。
- 每个 Release = 一次 CI（约 2 分钟）+ 210 MB 上传。值钱的是**内容**，不是版本号。
- 版本号是稀缺资源：被文案和小修吃掉之后，用户看不出哪个版本值得升级。

## 发版清单（真要发的时候）

1. `python tools/fill_interface.py --version vX.Y.Z --interface assets/interface.json`
2. `python tools/check_version.py --tag vX.Y.Z`（必须绿）
3. `python tools/publish_public.py` → `verify_no_pii.py --rev <commit>`（PII + SHAPE 双绿）
4. `git push --force-with-lease origin <commit>:main`
5. `git tag vX.Y.Z <commit>` → `git push origin refs/tags/vX.Y.Z`
6. 等 CI 双绿，`gh release view vX.Y.Z` 核对资产名/大小/digest

## 反例（本仓真实发生过的）

- v1.0.2：只改了 `interface.json` 里一句任务描述（去掉账号代号）→ **0 下载**，应该只提交。
- v1.0.3：清了注释/夹具名/4 个文件名里的代号 → **0 下载**，内容是对的，但应该等下一次真发版。
