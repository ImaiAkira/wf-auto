# 场景目标由配置声明，导航由引擎负责

## 背景

现状把**目标**和**导航**揉在同一处：39 个领主战类成员各占 `interface.json` 的一个手写选项，而"从当前页面怎么走到目标"写在一张 32 项优先级的中心分派表里（`SpecialEntry.next`），30 个节点的 `next` 全指回它。加一个成员要同时动选项列表、大分派表和 OCR 参数。

## 决定

- 场景配置**只声明目标**（打哪个成员、哪个难度），不描述怎么走。
- **导航由引擎负责**：从任意当前页面出发规划到目标的路径，包括纠错、撤退、重进。
- 因此流程被表达为**链式拓扑**：每段的 `next` 是显式后继，不再是优先级分派表。
- 跨场景的通用异常**不参与链的形状**：由配置层单独定义、统一注入（见 ADR-0001 的"注入"）。

## 考虑过的选项

- **(a) 用户显式选 + 中心枢纽分派（现状）**：加成员要改 option 列表与大分派表；"当前走到哪一步"是隐式的；分派表顺序本身携带知识。
- **(b) 引擎完全自动判定该进哪个场景**：用户失去指定目标的能力。
- **(c) 本决定。**

## 后果

- 链式拓扑必须补回中心枢纽天然具备的**自恢复**：需要显式的恢复边（`on_error` 回到已知页面），否则鲁棒性会不如现在。
- 异常组的注入是配置层的职责且必须幂等。一旦有人手改某个节点上的异常候选，链与注入就会互相打架，所以校验器要能抓这种漂移。
